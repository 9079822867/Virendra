VIRENDRA Mobile App API

13 JSON endpoints for the retailer mobile app: login, wallet, recharge, commission, reports and complaints.

Overview

Every endpoint is POST with Content-Type: application/json under:

Base URL
https://<your-domain>/App/webservice/
  1. Call Login with username and password. The reply carries TOKENID.
  2. Send it as Tokenid (TokenID for RechargeCall) on every other call.
  3. A new login replaces the token, so only the latest device stays signed in. On ERROR = 9, send the user back to Login.

Response keys come back exactly as written (ERROR, STATUSCODE, MESSAGE), not camelCase. Response dates use yyyy-MM-dd HH:mm:ss. Request dates accept yyyy-MM-dd, dd-MM-yyyy or dd/MM/yyyy.

Error codes

Check ERROR first: 0 means the call was handled, even when the result is a failed recharge or an empty list. Account endpoints (ChangePass, ResendOTP, ForgetPass, BookComplain) use Error / Status / Message instead.

ERRORMeaningApp should
0Request handledRead STATUSCODE / MESSAGE
2Record not found, user inactive, or OTP expiredShow MESSAGE
3User locked, wrong old password, or wrong OTPShow MESSAGE
4Wrong password at loginShow remaining attempts from MESSAGE
5Unexpected server errorRetry later; for a recharge, check the report first
9Authentication error (token missing, wrong or replaced)Go back to Login
10Invalid amountFix the amount
11Missing or invalid parametersFix the request
12Wrong transaction PINAsk for the PIN again

STATUSCODE: 1 = success, 2 = failed or processing. RechargeCall also uses 3 = failed.

POST/App/webservice/RechargeCallTokenIDalso /Recharge

Runs the same pipeline as the web Recharge page: validation, routing, vendor call, and switching to the next vendor when one fails.

Request
{
  "TokenID": "3f9c0b…",
  "MobileNo": "9876543210",
  "Operator": "1",
  "CircleId": "5",
  "Amount": "199",
  "Pin": "12345",
  "RefTxnId": "APP1001"
}
Response
{
  "ERROR": "0",
  "STATUS": "Recharge SUCCESS",
  "STATUSCODE": "1",
  "MESSAGE": "Recharge successful. …",
  "WBalance": "1051.00",
  "RECID": "8812",
  "TXNID": "APP1001",
  "OPERATORTXNID": "BR0001"
}
FieldRule
MobileNo6–15 digits
OperatorId from Operator
CircleId (or CricleID)Optional; filled by validation when blank
AmountGreater than 0, up to 99,999
PinChecked only when the user has a PIN set
RefTxnIdOptional; generated when blank
STATUSCODESTATUSWallet
1Recharge SUCCESSDebited
2Recharge Under ProcessingDebited; final status comes later
3Recharge FAILEDRefunded (or never debited if validation failed)

How the debit works:

  1. Token, PIN and amount are checked; then the validation SP builds the vendor route list. A rejection here fails with nothing debited.
  2. The first vendor try debits the wallet once.
  3. Vendor reply success → done. processing or no response tag matched → stays processing.
  4. Vendor reply failed → the next vendor is tried, with no second debit.
  5. No vendor left → marked failed and the debit is refunded.
When ERROR is 5, the wallet may already be debited. Show the RechargeReport instead of retrying.

Complaints

POST/App/webservice/BookComplainTokenid

One complaint per recharge, only on the user's own successful recharge.

Request
{
  "Tokenid": "3f9c0b…",
  "RecID": "8812",
  "Remark": "Recharge success but not credited"
}
Response
{
  "Error": "0",
  "Status": "1",
  "Message": "Your Complain Successfully Submitted"
}

RecID accepts the RecId from RechargeReport, our reference id, or the user's txn id.

MessageWhen
Your Complain Successfully SubmittedSaved (Status 1)
Recharge id not found, try againNo such recharge for this user
Sorry, Transaction ID Failed or Recharge Not SuccessRecharge is failed or still pending
Already complain doneA complaint already exists for it

The complaint is saved in Complaint (status Pending) and forwarded to the vendor's ComplainRequest URL when one is set. The vendor's reply, or its error, is stored in Complaint.ApiResponse; a vendor error does not fail the complaint.

Setup notes

SMS for OTP is not connected yet. SendOtpSms() in MobileAppController is empty, so ForgetPass can't reach users. The OTP is saved in User.OTP and never returned by the API.
  • Username = mobile number. The User table has no mobile or email column, so MOBILENUMBER and SHOPNAME repeat the username and EMAIL is blank.
  • PIN is compared as plain text with User.UserPin; users without a PIN can recharge without one.
  • Status ids: 1 = Success, 2 = Failed, 3 = Pending (RechargeStatusCodes). They must match usp_UpdateRechargeStatus.
  • MediumId: app recharges are saved with MediumId = 1, the same as the web panel.
  • Not built yet: ComplainList, Profile, wallet requests and member endpoints from the STC app.
